# Model-agnostic benchmark protocol

Submission contract: a process receives only `input.parquet` and writes `output.jsonl` records with `asset_id`, `window_start`, `window_end`, and `irregularity_score` in `[0,1]`. Optional `classification` and `evidence` are descriptive. The platform imports no detector implementation.

`ot-lab benchmark --run runs/cnc-0042 --predictions results/model-a.jsonl --output results/model-a` evaluates event intervals and the expected asset sampling grid. A prediction counts for an event when alert coverage reaches the configured overlap threshold (default 10%); the score threshold defaults to 0.5. It writes event precision/recall/F1, timestamp-level precision/recall/F1 and average precision (`window_pr_auc`), event detection rate, false-positive alert-window count, non-event alert duration, false alarms per asset-hour/day, first-detection latency, and event coverage. The generic `precision`/`recall`/`f1` fields alias event metrics. Event precision, recall, F1 and event detection rate are `null` for a normal-only run because event-level rates are undefined without ground-truth events; false-positive counts/rates remain available. Timestamp metrics use `started_at`, `duration_s`, `sampling_interval_ms`, and `asset_ids` from run metadata, so telemetry gaps remain expected negative samples.

Metric definitions:

- Event intervals and prediction windows are half-open `[start, end)`. Event detection is binary per ground-truth event. Its coverage is the union duration of intersecting thresholded alert windows divided by the event's observed duration. An event is detected when coverage reaches the configured overlap threshold. Timestamp metrics include a cadence point at the start and exclude one exactly at the end.
- Event recall is detected events divided by all events. Event precision uses detected events as true positives and thresholded alert windows whose overlap with any event is below the threshold as false positives. This combines event and alert-window units; read it with `event_detection_rate` and false-positive rates.
- `false_positive_windows` counts thresholded alert intervals that fail the overlap test. `false_positive_duration_s` counts their non-event portions after subtracting the union of ground-truth event intervals. Duplicate alerts can each contribute an FP window even if they cover the same non-event region.
- Timestamp metrics score every expected sample on the cadence grid for every declared asset, including telemetry gaps. A sample is labeled positive when its timestamp lies in a ground-truth event interval. The highest covering alert score is used for that sample.
- `window_pr_auc` and `pr_auc` are non-interpolated average precision over those expected timestamp samples, not trapezoidal PR area. The “window” name refers to one expected sample position, not one input alert record.
- Detection latency is measured from the event's observed start to the first intersecting alert; event coverage and detection rate are reported separately.
- Rates per asset-hour/day divide false-positive alert windows by run duration times declared asset count. They do not account for asset-specific operational exposure.

Use `ot-lab compare --run runs/cnc-0042 --predictions results/model-a.jsonl results/model-b.jsonl --output results/comparison` to score multiple prediction files against the same run and create `comparison.json` plus per-model reports. Compare models on identical telemetry and thresholds, and report both event and timestamp metrics. Never choose generator parameters based on a submission's score.

For dataset generation, `ot-lab dataset create --suite SUITE --runs N --seed SEED --workers N --output DATASET` generates independent runs in worker processes. The default is `--workers 1`; increasing it changes scheduling only, not the per-run seed plan or generated artifacts. Resumable checkpoints record the worker count used most recently but allow it to change on resume. Worker counts must be positive and cannot exceed the host's reported CPU count. The manifest records `generation_workers` and the exact command.

An indicative Windows workstation measurement on 2026-10-03 used `normal-operation-v0.1.yaml`, seed 4242, and 60 runs: 1 worker took 7.79 s (7.71 runs/s), 2 workers 5.15 s (11.66 runs/s), and 4 workers 4.34 s (13.83 runs/s). All three outputs had identical per-run telemetry/ground-truth hashes and byte-identical partition Parquet files (11,335,811 total bytes). This is one small benchmark on one host; use it to compare worker settings on your own storage and workload, not as a throughput guarantee. Large datasets still require storage and runtime capacity checks.

Reference tests cover full, partial, duplicate, and non-overlapping alert windows plus no-alert predictions. A protocol-conformance fixture also runs two independent external commands and compares their event and expected-sample metrics. These fixtures verify command/output plumbing; they do not establish real detector quality or substitute for benchmarking independently maintained models. See [ROADMAP.md](ROADMAP.md) for the remaining external-model validation.

`ot-lab run-container --run RUN_DIR --image IMAGE --output predictions.jsonl` uses Docker with `--pull=never`, no container network, read-only root, dropped capabilities, no-new-privileges, non-root uid, resource limits, minimal environment, and only a copied telemetry file plus one mounted output file. `--ulimit fsize` caps the mounted prediction file at `--max-output-bytes` in the container process tree; `--log-driver=none` prevents model stdout/stderr from accumulating in the daemon's container log. The image must already be present locally; the evaluator does not ask the daemon to contact a registry. A cidfile lets the runner force-remove a container if the Docker CLI exits on timeout or output-size limit. Ground truth and sibling files are not mounted. The default output ceiling is 64 MiB; retained process logs are separately bounded. A Docker 29.8.1 local smoke confirmed the process-tree file-size limit stopped a repeated-write submission at exactly 1,024 host-file bytes with `EFBIG`/`File too large`. These controls do not replace a threat model: daemon/host compromise, kernel escape, image contents that already include extra data, and adversarial Docker/runtime behavior remain outside the guarantee. `ot-lab run-model` is a convenience for trusted local commands only and does not isolate filesystem or network access. `ot-lab challenge --suite TRAINING_SUITE --challenge-suite suites/challenge-v0.1.yaml --image IMAGE --output RESULTS` samples a fresh hidden seed and scenario from the separate challenge distribution, runs the container, scores its output, then removes the temporary case. Only `metrics.json` and `report.html` are retained. `--challenge-suite` is optional for compatibility; when omitted, cases use the supplied suite's distribution.
