# Model-agnostic benchmark protocol

Submission contract: a process receives only `input.parquet` and writes `output.jsonl` records with `asset_id`, `window_start`, `window_end`, and `irregularity_score` in `[0,1]`. Optional `classification` and `evidence` are descriptive. The platform imports no detector implementation.

`ot-lab benchmark --run runs/cnc-0042 --predictions results/model-a.jsonl --output results/model-a` evaluates event intervals and the expected asset sampling grid. Metrics are versioned in `metrics.json`; the current event metric contract is `2.0.0`. A prediction counts toward an event when the union of thresholded alert intervals covers at least the configured fraction of that event (default 10%); the score threshold defaults to 0.5. Thresholded windows on one asset are coalesced into alert episodes when they overlap, touch, or have a gap no greater than `--alert-merge-gap-seconds` (default 0 seconds).

Event precision and recall now use consistent event/episode units. An event must meet the configured coverage threshold across all its thresholded alert windows, and its matched episode must individually cover at least that fraction of the event. A deterministic maximum-cardinality one-to-one match then pairs eligible ground-truth events and alert episodes. One long alert cannot claim multiple events; duplicate/fragmented alerts around one event do not create multiple true positives, and several individually sub-threshold episodes cannot qualify one another by adding their coverage together. Event precision is matched alert episodes divided by all thresholded alert episodes; event recall is matched events divided by all ground-truth events; event F1 is their harmonic mean. The default zero gap joins overlapping or adjacent windows; choose a positive gap only when that alert-coalescing tolerance is part of the benchmark definition, and keep it identical across submissions.

The `false_positive_windows` count and `false_positives_per_asset_hour/day` remain window-level diagnostics: each thresholded input window is false if its overlap with the union of any same-asset ground-truth events is below the overlap threshold. `false_positive_alert_episodes` and `false_positive_alert_episodes_per_asset_hour` separately count unmatched coalesced episodes. Event precision/recall/F1 and event detection rate are `null` for normal-only runs; episode/window false-positive counts and rates remain available. The generic `precision`/`recall`/`f1` fields alias v2 event metrics.

Timestamp-level precision/recall/F1 and `window_pr_auc` are unchanged by event episode matching. They score the expected asset sampling grid from `started_at`, `duration_s`, `sampling_interval_ms`, and `asset_ids` in run metadata; telemetry gaps remain expected negative samples. `window_pr_auc` is non-interpolated average precision over expected sample positions, not trapezoidal area or input alert records. Detection latency uses the event's observed start and the first intersecting thresholded alert; coverage and matched event detection are reported separately.

Metric definitions:

- Event intervals and prediction windows are half-open `[start, end)`. An event's coverage is the union duration of intersecting thresholded alert windows divided by the event's observed duration. `coverage_threshold_met` is true when this reaches the configured overlap threshold; `detected` is true only if a one-to-one episode/event match is assigned. Timestamp metrics include a cadence point at the start and exclude one exactly at the end.
- Event precision/recall/F1 use v2 one-to-one matching between coverage-qualified events and coalesced alert episodes. `coverage_threshold_met` records aggregate event coverage; the matched episode must also individually meet the overlap threshold; `detected` records whether the event received a one-to-one alert-episode match.
- `false_positive_windows` counts thresholded alert intervals that fail the overlap test. `false_positive_duration_s` counts their non-event portions after subtracting the union of ground-truth event intervals. Duplicate alerts can each contribute an FP window even if they cover the same non-event region.
- Alert episodes are formed after thresholding, independently per asset. Their gap merge parameter is included in `metrics.json`; comparisons should use the same value.
- Timestamp metrics score every expected sample on the cadence grid for every declared asset, including telemetry gaps. A sample is labeled positive when its timestamp lies in a ground-truth event interval. The highest covering alert score is used for that sample.
- `window_pr_auc` and `pr_auc` are non-interpolated average precision over those expected timestamp samples, not trapezoidal PR area. The “window” name refers to one expected sample position, not one input alert record.
- Detection latency is measured from the event's observed start to the first intersecting alert; event coverage and detection rate are reported separately.
- Rates per asset-hour/day divide false-positive alert windows by run duration times declared asset count. They do not account for asset-specific operational exposure.

## Metric design and references

Time-series events span intervals, so a benchmark should make its event matching, overlap, fragmentation and timing rules explicit. Tatbul et al. formalize range-based precision and recall with configurable overlap, positional and cardinality preferences; OT Irregularity Lab's v2 event score is a separate contract, not a direct implementation of their RP/RR equations. It reports coverage and latency alongside one-to-one event/alert-episode matching to expose partial detection, duplicate alarms and misses without collapsing these trade-offs into one number. The affiliation-metric study also documents that time-series scoring choices can produce unintuitive or gameable comparisons; treat each metric as a defined view of performance, not an objective measure of detector quality.

`window_pr_auc` uses non-interpolated average precision over expected cadence positions. Its step-wise weighting follows the standard AP definition `sum((recall_n - recall_(n-1)) * precision_n)`; this is intentionally distinct from trapezoidal area under a PR curve. The challenge-level `pr_auc` is the macro mean of per-case average precision among cases with positive samples, so each eligible case has equal weight.

References:

- Tatbul, N. et al. (2018), [Precision and Recall for Time Series](https://papers.nips.cc/paper_files/paper/2018/hash/8f468c873a32bb0619eaeb2050ba45d1-Abstract.html), NeurIPS 31. Provides range-based precision/recall with explicit domain choices; cited as motivation, not as the exact OT Lab formula.
- Huet, A., Navarro, J. and Rossi, D. (2022), [Local Evaluation of Time Series Anomaly Detection Algorithms](https://arxiv.org/abs/2206.13167), KDD '22. Reviews limits and design choices of point and event metrics and proposes affiliation metrics.
- scikit-learn, [`average_precision_score`](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html). Documents non-interpolated average precision and its difference from trapezoidal PR area.

Always publish the `metric_version`, score threshold, overlap threshold, alert merge gap, partition/suite versions and challenge case count with reported scores. Compare submissions on the same generated cases or the same hidden challenge distribution and keep all thresholds fixed. Report event, cadence-level and false-positive-rate metrics together; do not select simulator settings to improve one submission's result.

Use `ot-lab compare --run runs/cnc-0042 --predictions results/model-a.jsonl results/model-b.jsonl --output results/comparison` to score multiple prediction files against the same run and create `comparison.json` plus per-model reports. Compare models on identical telemetry and thresholds, and report both event and timestamp metrics. Never choose generator parameters based on a submission's score.

For dataset generation, `ot-lab dataset create --suite SUITE --runs N --seed SEED --workers N --output DATASET` generates independent runs in worker processes. The default is `--workers 1`; increasing it changes scheduling only, not the per-run seed plan or generated artifacts. Resumable checkpoints record the worker count used most recently but allow it to change on resume. Worker counts must be positive and cannot exceed the host's reported CPU count. The manifest records `generation_workers` and the exact command.

An indicative Windows workstation measurement on 2026-10-03 used `normal-operation-v0.1.yaml`, seed 4242, and 60 runs: 1 worker took 7.79 s (7.71 runs/s), 2 workers 5.15 s (11.66 runs/s), and 4 workers 4.34 s (13.83 runs/s). All three outputs had identical per-run telemetry/ground-truth hashes and byte-identical partition Parquet files (11,335,811 total bytes). This is one small benchmark on one host; use it to compare worker settings on your own storage and workload, not as a throughput guarantee. Large datasets still require storage and runtime capacity checks.

Reference tests cover full, partial, duplicate, and non-overlapping alert windows plus no-alert predictions. A protocol-conformance fixture also runs two independent external commands and compares their event and expected-sample metrics. These fixtures verify command/output plumbing; they do not establish real detector quality or substitute for benchmarking independently maintained models. See [ROADMAP.md](ROADMAP.md) for the remaining external-model validation.

`ot-lab run-container --run RUN_DIR --image IMAGE --output predictions.jsonl` uses Docker with `--pull=never`, no container network, read-only root, dropped capabilities, no-new-privileges, non-root uid, resource limits, minimal environment, and only a copied telemetry file plus one mounted output file. `--ulimit fsize` caps the mounted prediction file at `--max-output-bytes` in the container process tree; `--log-driver=none` prevents model stdout/stderr from accumulating in the daemon's container log. The image must already be present locally; the evaluator does not ask the daemon to contact a registry. A cidfile lets the runner force-remove a container if the Docker CLI exits on timeout or output-size limit. Ground truth and sibling files are not mounted. The default output ceiling is 64 MiB; retained process logs are separately bounded. A Docker 29.8.1 local smoke confirmed the process-tree file-size limit stopped a repeated-write submission at exactly 1,024 host-file bytes with `EFBIG`/`File too large`. These controls do not replace a threat model: daemon/host compromise, kernel escape, image contents that already include extra data, and adversarial Docker/runtime behavior remain outside the guarantee. `ot-lab run-model` is a convenience for trusted local commands only and does not isolate filesystem or network access.

`ot-lab challenge --suite TRAINING_SUITE --challenge-suite suites/challenge-v0.2.yaml --image IMAGE --cases 100 --output RESULTS` generates and evaluates 100 independent hidden cases. Each inference gets a fresh container with only that case's telemetry input and output mount; labels, seeds, resolved scenarios and other cases stay outside the container. On normal completion or a Python-managed error, the temporary case directory, predictions and per-case metrics are removed. Abrupt host termination may leave the operating system's temporary directory behind. The command itself writes only pooled `metrics.json` and `report.html`. Event counts and event precision/recall are pooled across cases; false-positive rates divide pooled counts by total asset-hour exposure; event means are weighted by event count. Expected-sample PR-AUC is a macro average of per-case average precision, excluding cases with no positive samples. `--cases` defaults to 1 for compatibility, and `--threshold`, `--overlap`, and `--alert-merge-gap-seconds` define one shared scoring contract for every case. The challenge distribution is a benchmark choice, not estimated industrial prevalence.

A three-case runtime smoke with the local reference adapter and `challenge-v0.3` is recorded in [the challenge/Docker smoke record](docs/workflows/synthetic-dataset-generation/runs/2026-10-04-challenge-docker-3case-smoke.md). It checks orchestration and aggregate-only persistence; its model scores are not used to alter the simulator or challenge distribution.
